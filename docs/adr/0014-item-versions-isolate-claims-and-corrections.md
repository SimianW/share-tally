# Item versions isolate claims and corrections

Issue #1 requires explicit stale-client behavior. For item claims and item corrections, the owner chose per-item versions instead of the bill-wide revision: participants own their claims (ADR-0001), so another participant's saved claim must not block a save unless their combined claims exceed an item. Initiators likewise must be able to correct prices while participants claim. Transactions still serialize mutations and check exact fractions, including reservations; partial allocation is allowed.

An item's version is the bill revision of the edit that created it or last changed its final cost or name; items on a newly initiated bill start at 1. Claims do not change it. Because the bill revision only increases, an item re-added under the id of a removed item never matches a review of the removed one. The comparison happens when either initiated-item editor writes the item. Changes to receipt tax, discounts or other allocations count if they change an item's final cost, including sibling costs submitted by the legacy whole-list editor. Derivation-only edits with the same final cost and name do not advance it. Receipt corrections still use the frozen derivation in ADR-0009, without reallocating siblings. Price changes still invalidate only that item's confirmations, retaining reservations (ADR-0007); name-only changes preserve existing confirmations.

Claim confirmation sends `{ reviewedItems: [{ itemId, version }], claims: [{ itemId, numerator, denominator }] }`. Reviewed items describe the complete item list the participant saw, not just their picks. The server checks versions only for selected items, reports current items missing from the reviewed list as added, and reports selected items no longer present as removed. Unselected changed or removed items do not block. A single-item correction sends `{ version, ...correctionFields }` for that item. A whole-list correction sends `{ reviewedItems: [{ itemId, version }], items: [...] }`, checking every reviewed version and the complete item set before applying additions, deletions or corrections. These requests no longer accept a bill revision.

Conflict responses preserve the human-readable `error` and add `conflicts: { stale: [...], overAllocated: [...] }`. A stale entry is `{ itemId, kind: 'changed', finalCents, name }`, `{ itemId, kind: 'added' }` or `{ itemId, kind: 'removed' }`. A capacity entry is `{ itemId, available: { numerator, denominator } }`, where availability includes this participant's existing fraction and excludes everyone else's confirmed and reserved claims. Both fraction components are decimal integer strings, preserving exact rational arithmetic even when combined denominators exceed JavaScript's safe integer range. All stale and capacity conflicts are collected in the same 409, including both kinds on the same item. Corrections use the same stale entries with an empty capacity list. Unrelated 409s, such as final bills, need not carry item conflicts.

Completed and canceled bills remain final. An identical claim retry can still succeed without a second financial effect, including after completion, provided its reviewed selections and item set remain current; canceled bills never accept retries. Other bill-level actions, including manual shares, bill edits and cancellation, retain the bill-wide revision. Successful item mutations still advance that revision for those consumers, and notify the group after commit. SSE remains invalidation-only `changed` events followed by a refetch; this decision does not introduce a new transport or the per-item attention UI in #154.
