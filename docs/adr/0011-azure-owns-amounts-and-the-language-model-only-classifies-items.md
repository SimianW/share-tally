# Azure owns amounts; the language model only names items and judges taxability

Receipt interpretation has two stages. Azure Document Intelligence is the sole, deterministic source of every amount: item prices and quantities, subtotal, tax, total and discounts. A language model then makes one call per receipt, receiving the structured evidence (no image) and returning exactly two things per item: a plain-English everyday name and whether the item is taxable. It never produces or changes amounts, and it makes no other judgements, such as whether a line is really an item. Its taxability verdict is trusted as given, even where printed tax codes are present, because the model receives those codes as evidence. This supersedes #26's rule that printed receipt markers take priority over model suggestions.

While the model runs, the bill draft is processing: the initiator can view the Azure result but cannot edit or initiate it, although they can start other bills. If the model does not return within 40 seconds, fails, returns an unusable result, or the server restarts during processing, every item without a usable answer is treated as taxable and keeps its Azure name, and the initiator is told that the AI tax check did not finish and asked to confirm each item's taxability. The model is not retried. Locking edits during processing was chosen over merging late results into user edits, because the model is fast and field-level merging adds complexity for little gain. This supersedes #26's rules that name interpretation can be retried and that initiation need not wait for it. (Amended by #50: the deadline was 20 seconds, but the receipt benchmark showed large receipts taking 15–24 seconds, so it is 40 seconds with low reasoning effort.)

The bill uses a single tax rate: Azure's printed rate when it reports exactly one, otherwise receipt tax divided by the taxable amount (ADR-0009). Receipt tax is always allocated in full, so a wrong taxability verdict shifts tax between items but never changes the bill's total tax.
