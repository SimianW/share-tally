# Attach receipt discounts by generic rules, guarded by reconciliation

Azure's receipt model has no discount field. Observed receipts show discounts either as separate negative-amount lines (Costco coupons, each directly after its item and quoting its product code) or as savings text merged into the discounted item's own line while its price stays undiscounted. Discounts are attached deterministically, with no merchant-specific parsing and no language model: a negative line that quotes an item's product code becomes that item's own discount; otherwise a negative line directly after an item becomes that item's discount; and a negative amount following the price inside an item's own line becomes that item's discount. The result is accepted only if the items then reconcile to the receipt subtotal within one cent. Otherwise the whole receipt falls back: negative lines become a receipt-wide discount, merged savings text is left for the initiator to enter, and any remaining gap is shown by the reconciliation bar rather than being absorbed as a discount, because a gap can equally mean a missed item.

Spreading every discount across all items (the simpler baseline) was rejected because it charges one person's coupon to everyone. Letting the language model attach discounts was rejected because it would give the model control over amounts (ADR-0011). Showing matches only as suggestions for the initiator to confirm was rejected as extra work, since the reconciliation check already guards against wrong attachments.
